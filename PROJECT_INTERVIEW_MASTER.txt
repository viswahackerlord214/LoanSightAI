3. EVERY FEATURE IN THE PROJECT
============================================================

FEATURE NAME: Dynamic Dataset Upload & Training
PURPOSE: Allow users to upload their own loan dataset and train the ML model on the fly.
USER ACTION: User navigates to /upload, selects a CSV, and clicks submit.
FRONTEND: `upload.html` shows a drag-and-drop zone and a fake animated loading overlay.
BACKEND: `app.py` -> `upload()` saves the file to `uploads/` and calls `train_and_save_model()`.
ML PIPELINE: `train_model.py` reads CSV, determines target column (`default` or `loan_paid_back`), drops IDs, one-hot encodes categoricals, scales, trains Random Forest, and saves `.pkl` files.
OUTPUT: Updates global variables in `app.py` and flashes success message.

FEATURE NAME: Customer Search (AJAX)
PURPOSE: Look up existing customers from the uploaded dataset to autofill the prediction form.
USER ACTION: Types name/ID in `/search` and hits enter.
FRONTEND: Vanilla JS `fetch()` call to `/search_customer?q=...`. Renders results dynamically.
BACKEND: `app.py` -> `search_customer()`. Searches the Pandas DataFrame (`uploaded_df`) using string contains mask.
OUTPUT: Returns top 10 matching rows as JSON. User clicks "Use for Prediction" which saves data to browser `sessionStorage` and redirects to `/predict`.

FEATURE NAME: Loan Repayment Prediction
PURPOSE: Predict if an applicant will repay the loan.
USER ACTION: Submits the form on `/predict`. (Can be auto-filled via sessionStorage JS script).
FRONTEND: Form with HTML5 validation and dynamic hints.
BACKEND: `app.py` -> `predict()`. Gathers form data, creates a 1-row Pandas DataFrame, applies `pd.get_dummies()`, aligns columns with `_features_list` (padding missing with 0s), scales via `_scaler.transform()`, and runs `_model.predict_proba()`.
PROCESSING: 3-Tier Risk Logic determines outcome based on `default_probability`: <30% Likely to Repay, 30%-60% Needs Review, >60% High Default Risk.
OUTPUT: Saves result to Flask `session` and renders `result.html`.

FEATURE NAME: PDF Report Generation
PURPOSE: Export prediction results to a printable PDF.
USER ACTION: Clicks "Download PDF Report" on the result page.
FRONTEND: Standard href link to `/download_report`.
BACKEND: `app.py` -> `download_report()`. Reads `session["last_result"]`. Uses ReportLab to programmatically draw a styled PDF with tables, headers, and AI summaries. Returns file via `send_file()`.

5. END-TO-END APPLICATION FLOW
============================================================

FLOW 1: APPLICATION STARTUP
1. Python executes `app.py`.
2. App attempts to load `model_rf.pkl`, `scaler_rf.pkl`, and `columns_rf.pkl`.
3. If successful, sets `is_model_trained = True`. If not, sets to False.
4. Flask server starts on port 5000.

FLOW 2: DATASET UPLOAD & TRAINING
1. User visits `/upload`.
2. User submits a CSV file.
3. Backend saves to `uploads/filename.csv`.
4. Backend calls `train_and_save_model(filepath)`.
5. `train_model.py` executes ML pipeline (Pandas -> StandardScaler -> RandomForest).
6. Pickles are saved to disk.
7. `app.py` reloads the new pickles into global memory.
8. User is redirected to `/upload` with a success flash message.

FLOW 3: CUSTOMER SEARCH
1. User visits `/search`.
2. Types query "John". JS sends `GET /search_customer?q=john`.
3. Backend filters in-memory `uploaded_df` for string match in name/id columns.
4. Returns JSON array of matches.
5. Frontend renders cards.
6. User clicks "Use". JS saves JSON record to `sessionStorage('prefill')` and redirects to `/predict`.

FLOW 4: PREDICTION
1. User visits `/predict`. JS reads `sessionStorage`, maps keys to form inputs, and fills them.
2. User clicks Submit. Form POSTs to `/predict`.
3. Backend extracts features, applies dummy encoding, aligns columns to match training schema.
4. Backend scales data and runs `model.predict_proba()`.
5. Evaluates 3-Tier logic.
6. Saves `prediction`, `probability`, and `input_data` to Flask `session`.
7. Renders `result.html`, which uses Chart.js to animate the probability bar.

FLOW 5: REPORT GENERATION
1. User clicks "Download PDF" on results page.
2. GET `/download_report`.
3. Backend retrieves data from Flask `session`.
4. ReportLab constructs the document (tables, styles, logic text).
5. PDF is returned as an attachment via `send_file`.

10. FEATURE ENGINEERING
============================================================

NAME: Categorical Encoding
FORMULA: `pd.get_dummies(..., drop_first=False)`
INPUT FEATURES: `gender`, `marital_status`, `education_level`, `employment_status`, `loan_purpose`, `grade_subgrade`, `employment_type`
WHY IT EXISTS: Random Forest in scikit-learn requires numerical inputs; it cannot natively process string categories.
WHERE CREATED: `train_model.py` during training, and mirrored in `app.py` during inference.

NAME: Feature Alignment (Dummy Padding)
FORMULA: `df_encoded[col] = 0` for missing columns.
WHY IT EXISTS: During inference, a single applicant might only have one category (e.g., `loan_purpose_MEDICAL`). The model expects ALL dummy columns generated during training (e.g., `loan_purpose_EDUCATION`, etc). This logic ensures the inference vector shape exactly matches the training vector shape.

NAME: Credit Score Proxy (in `app.py`)
FORMULA: `float(form.get("loan_int_rate", 650)) * 50`
WHY IT EXISTS: Hardcoded logic in `app.py` `/predict` route trying to map standard form fields to expected backend features. It uses interest rate as a proxy for credit score if not explicitly provided.

18. PERFORMANCE & SCALABILITY
============================================================

CURRENTLY IMPLEMENTED:
- Single-threaded, stateful design. 
- In-memory Pandas DataFrame (`uploaded_df`).

BOTTLENECKS & SCALABILITY ISSUES:
- FLASK GLOBAL VARIABLES: Storing `uploaded_df` and `is_model_trained` in global variables will fail entirely if deployed via a WSGI server like Gunicorn with multiple workers (each worker will have a different memory state).
- MEMORY LEAK / LIMIT: Loading large CSVs into RAM will crash the server.
- BLOCKING I/O: Model training (`train_and_save_model`) is synchronous and blocks the main Flask thread.
- FIX: Move data to a real database (PostgreSQL), move training to a background worker (Celery/Redis), and load model state lazily or via a dedicated inference service.

21. INTERVIEW QUESTIONS
============================================================

LEVEL 1 — BASIC
QUESTION: What does `app.py` do in this project?
WHAT INTERVIEWER IS TESTING: Basic understanding of Flask routing and project structure.
KEY CONCEPTS: Routing, WSGI, templates.
STRONG ANSWER: It's the main Flask application that defines the HTTP endpoints, handles file uploads, processes form submissions for predictions, loads the pickled ML models to run inference, and generates PDF reports.

LEVEL 2 — INTERMEDIATE
QUESTION: How did you handle categorical variables in your ML pipeline?
WHAT INTERVIEWER IS TESTING: Data preprocessing knowledge.
KEY CONCEPTS: One-Hot Encoding, Dummy Variables, Feature Alignment.
STRONG ANSWER: I used Pandas `get_dummies` to one-hot encode categorical features. Crucially, during inference, I aligned the generated columns with a saved `columns_rf.pkl` list to ensure the incoming data vector exactly matched the shape of the data the Random Forest was trained on, filling missing category columns with zeros.

LEVEL 3 — ADVANCED
QUESTION: Your application uses global variables to store the uploaded dataset (`uploaded_df`). What happens if we deploy this to Production using Gunicorn with 4 worker processes?
WHAT INTERVIEWER IS TESTING: System design, WSGI architecture, statelessness.
KEY CONCEPTS: WSGI workers, shared memory, stateless APIs.
STRONG ANSWER: It will break. Each Gunicorn worker has its own memory space. If a user uploads a CSV to Worker A, `uploaded_df` is set there. If their subsequent search request hits Worker B, `uploaded_df` will be None, causing an error. To fix this, state must be moved out of memory into a Database (like PostgreSQL or Redis) and model artifacts should be loaded independently by each worker or served via a separate inference API.

LEVEL 4 — DEEP TECHNICAL
QUESTION: Why did you use `class_weight='balanced'` in your Random Forest?
WHAT INTERVIEWER IS TESTING: Understanding of imbalanced datasets in ML.
KEY CONCEPTS: Class imbalance, precision/recall.
STRONG ANSWER: In loan prediction, defaults (class 0) are usually a minority compared to repayments (class 1). If trained normally, the model might just predict "repay" for everyone to achieve high accuracy. `balanced` adjusts the weights inversely proportional to class frequencies, forcing the model to penalize misclassifications of the minority class (defaults) more heavily.

25. BUGS / WEAKNESSES / INTERVIEW TRAPS
============================================================

WHAT: Directory Traversal Vulnerability
WHERE: `app.py` -> `upload()` route. `filepath = os.path.join("uploads", file.filename)`
WHY: `file.filename` is taken directly from user input. A malicious user could upload a file named `../../../etc/passwd` and overwrite system files.
HOW TO IMPROVE: Wrap it with `werkzeug.utils.secure_filename(file.filename)`.

WHAT: Stateful Global Variables in WSGI
WHERE: `app.py` -> `global uploaded_df, is_model_trained`
WHY: Will fail in production environments with multiple workers.
HOW TO IMPROVE: Use a database to store datasets and a status flag.

WHAT: Hardcoded Fake Prediction Fallback
WHERE: `app.py` -> `predict()` route.
WHY: If the model isn't loaded but `is_model_trained` is true, it runs `prob_raw = float(np.random.random())`. This is a massive interview trap; do not claim the model is working if it's falling back to `random()`.
HOW TO IMPROVE: Return a 500 error or flash message "Model unavailable".

WHAT: Hardcoded Model Features mismatch
WHERE: `app.py` `predict()` lines 220-234.
WHY: The dictionary explicitly hardcodes features like `age`, `annual_income`, `credit_score` using wild guesses (e.g. `float(form.get("loan_int_rate", 650)) * 50`). This indicates the UI form fields don't perfectly match the backend dataset features natively, requiring manual hacky mapping.

"I built LoanSight AI using Flask, Python, and Scikit-Learn. The core feature is its dynamic adaptability: when a user uploads a CSV loan dataset, a script cleans the data, applies one-hot encoding, scales it, and trains a Random Forest Classifier on the fly, saving the artifacts using Pickle. The web app then loads these artifacts into memory. For the UI, I used Jinja2 templates styled with Tailwind CSS. When a user wants to predict a loan, they fill out a form, the backend dynamically aligns their input features with the expected model schema, scales the data, and runs `predict_proba()` to determine if they fall into a low, moderate, or high-risk tier. Finally, the user can download a dynamically generated PDF report."

3-MINUTE EXPLANATION (Technical):
"At an architectural level, LoanSight AI is a monolithic Flask application handling both the presentation layer and ML inference. 

When a user uploads data, `train_model.py` is invoked. It handles missing values, applies Pandas `get_dummies` for categorical encoding, and uses `StandardScaler`. I chose a Random Forest with `class_weight='balanced'` because loan default datasets are notoriously imbalanced. The trained model, scaler, and exact column schema are serialized via Pickle.

On the frontend, I implemented a search feature using Vanilla JS `fetch()` that queries the in-memory Pandas dataframe and returns JSON. If a user selects a profile, it saves the data to the browser's `sessionStorage` and pre-fills the prediction form.

When the form is submitted via POST, the Flask backend intercepts it. The trickiest part was feature alignment—because one-hot encoding generates variable columns depending on the training set, my backend dynamically creates a DataFrame from the user input, applies `get_dummies`, and then forces the DataFrame to match the exact column structure saved during training by padding missing columns with zeros. 

After scaling, `model.predict_proba()` returns a probability score, which dictates a 3-tier risk logic. The result is temporarily stored in a Flask secure cookie session. When the user requests a PDF, the `/download_report` route reads that session and uses ReportLab to draw a formatted PDF document.

While currently stateful and reliant on global variables—which wouldn't scale in a multi-worker production setup—it successfully demonstrates a complete end-to-end ML pipeline integrated directly into a web interface."
